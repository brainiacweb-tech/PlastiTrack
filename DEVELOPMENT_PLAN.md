# PlastiTrack Development Plan

## Product scope

PlastiTrack is a demonstration-ready plastic collection platform with a public product site and a protected operations application. The demo must make simulated device activity explicit; no physical hardware or production deployment is implied.

## Architecture

- **Web client:** React, Vite, TypeScript, Tailwind CSS, React Router, React Hook Form, Zod, Lucide React, and Recharts.
- **API:** Node.js, Express, TypeScript, REST endpoints, Zod request validation, JWT authentication, bcrypt password hashing, and server-side role authorization.
- **Persistence:** The browser demo stores its simulated users and operational scenario in local storage, so evaluation needs no server or database. The separately maintained API uses PostgreSQL through Prisma for users/roles, locations, bins/devices/readings, partners/collectors/tasks/records, plastic inventory, recycling companies/requests/deliveries, notifications, damage and collection requests, and audit events.
- **IoT boundary:** A device-ingestion API accepts authenticated device readings and records source and timestamp. The demo simulator calls the same service boundary, marks readings as simulated, and does not claim a hardware connection. MQTT/ESP32 integration can later publish into this boundary.
- **Authorization:** The local browser demo mirrors role-based access for demonstration only. The optional API enforces roles in middleware and scopes data access to the user's role and assignment; client-side guards alone are not production security.
- **Demo operations:** Seeded, clearly identified records and role-based demo accounts support monitoring, collection, recycling, and environmental reporting scenarios. A reset operation is development/demo-only.

## Application modules

1. Public pages: home, about, how it works, technology, impact, contact, login, and registration.
2. Identity and access: authentication, six roles, protected routes, permissions, and audit logging.
3. Smart bins: locations, device connectivity, fill thresholds, search/filter, details, and telemetry.
4. Device simulation: controlled fill changes, online/offline state, threshold alerts, and reading history.
5. Collection operations: recommendations, assignment, collector status lifecycle, completion weights, and bin reset.
6. Notifications: in-app read/unread history with contextual navigation.
7. Recycling marketplace: inventory, company demand, requests, and delivery status.
8. Analytics: collection totals, bin status, trends, regional/category performance, and CSV/PDF report export.
9. Demo guide: guided role scenarios and safe reset.

## Data model outline

- `User` belongs to a `Role`; optional partner/company relationships scope operational data.
- `BinLocation` has many `SmartBin`s. A bin has one `Device`, many `SensorReading`s, and many collection tasks/reports.
- `CollectionPartner` has many `Collectors`; `CollectionTask` links a bin to a partner and optionally a collector; `CollectionRecord` captures completed weight and evidence metadata.
- `PlasticCategory` classifies bins and inventory. `PlasticInventory` is generated by completed collection records and is reduced/reserved through `RecyclingRequest`s.
- `RecyclingCompany` owns requests and deliveries. Notifications and audit logs reference the actor and affected entity.
- Foreign keys, unique device/bin identifiers, indexed state/time/location fields, and created/updated timestamps are applied in Prisma.

## Permission model

| Role | Main access |
| --- | --- |
| Administrator | All modules, users, bins, configuration, reports, audit |
| Collection partner | Team, assigned areas/tasks, progress, operations reports |
| Waste collector | Assigned tasks, collection lifecycle, evidence, history |
| Recycling company | Available inventory, demand, requests, deliveries |
| Bin/location manager | Premises bins, damage/full reports, collection tracking |
| Environmental officer | Regional, collection, recycling, and impact analytics |

Endpoints declare allowed roles and scope records by partner, collector, company, or location where applicable. Role changes and sensitive demo actions are audited.

## Delivery phases

1. **Foundation:** scaffold, architecture, database schema, seed/reset strategy, auth, validation, errors, audit, and RBAC.
2. **Public experience:** design tokens, responsive site, navigation, product story, auth entry points.
3. **Operations shell:** protected routing, role-specific dashboards, user and bin management.
4. **Bins and IoT:** telemetry ingestion, explicit simulator controls, threshold transitions, connectivity, history.
5. **Collections and alerts:** assignment, status lifecycle, authorized completion/reset, notifications.
6. **Marketplace:** inventory discovery, demand, request lifecycle, delivery tracking.
7. **Analytics and reports:** meaningful filters/charts and CSV/PDF export.
8. **Competition demo:** role accounts, seeded scenarios, guided walkthrough, reset, end-to-end testing.

After each phase, run the smallest relevant tests/type checks, verify the connected API workflow, and review responsive behavior. Do not mark an unimplemented module complete.

## Integration and deployment decisions

- PostgreSQL and `DATABASE_URL`, JWT signing secret, and demo configuration are environment-only; never ship secrets to the client.
- The browser demo uses a local adapter and persists only to browser local storage. The optional API is a separate development component; API validation is authoritative when using its endpoints.
- Simulated readings and real-device readings share the same domain model but include an explicit source flag.
- Device identity and per-device credentials will be separate from user JWTs. Production MQTT broker, email/SMS/WhatsApp providers, object storage for evidence, and cloud hosting are future integrations.
- Use local development defaults only for non-sensitive values. The demo must clearly disclose simulation and demonstrate no real-world operational coverage.

## Current implementation status

The current scaffold includes the public site, role-aware application shell, browser-only demo login for all six roles, local persistence, bin registration and simulation, collection task progression, recycling inventory requests, notifications, analytics, and CSV export. The optional JWT-protected REST API, PostgreSQL/Prisma schema and initial migration, and database seeding/reset are also retained, but have not been exercised against a running PostgreSQL instance in this environment.

Still outstanding are full user/account and collection-team administration, account registration/invitations, damage and location collection-request workflows, collection evidence uploads, a live tile-based map, and a generated PDF report. The notification integrations and physical device hardware are also not connected. Do not present these as completed capabilities until implemented and tested.
